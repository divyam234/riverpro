# AGENTS.md

River Pro — a Go extension on top of [River](https://github.com/riverqueue/river) v0.38.0 (job queue) adding BatchWorker, Sequences, Ephemeral jobs, Workflows, DeadLetter, Durable Periodic Jobs, and global/per-partition concurrency limits.

## Layout

```
riverpro.go                 public API: Config, Client, NewClient, Pilot integration entry point
periodic_jobs.go            durable periodic jobs: Add/Get/List/Delete/Pause/Resume + enqueuer loop
pro_pilot.go                riverpilot.Pilot impl — injects Pro metadata + sequence handling on insert
pro_feature_matrix_test.go  end-to-end Pro feature tests (real DB)
riverpro_test.go            pure-Go unit tests for workflow preparation / config
cmd/riverpro/               migrate CLI binary (migrate-up / migrate-down / migrate-get)
driver/                     core Pro executor + Wrapper for both driver types
  driver.go                 ProExecutor / ProDriver interfaces + Executor methods
  internal/dbsqlc/          sqlc-generated code (DO NOT EDIT)
  migration/pro/            bundled Pro SQL migrations (line name: "pro")
  riverpropgxv5/            pgx/v5 driver wrapper + tests
  riverprodatabasesql/      database/sql driver wrapper + tests
  riverprodrivertest/       shared behavior test suite (Exercise[TTx])
riverworkflow/              workflow helpers (metadata keys, errors)
riverbatch/                 batch helpers
riverencrypt/riversecretbox NaCl secretbox job encryption
riverproshared/riverprosharedtest  test helpers (TestTxPgxPro, WaitExpectTimeout)
examples/                   runnable doc examples as tests
```

## Test setup

Tests require a running PostgreSQL. The helper `riversharedtest.TestDatabaseURL()` reads `TEST_DATABASE_URL` (falls back to a default `river_test` URL).

- Most packages call `riverdbtest.TestSchema` to get an isolated migrated schema per test; cleanup is automatic.
- Schemas are named like `<package>_<utc-timestamp>_schema_<NN>` and can be reused across subtests in the same process.
- To skip DB tests in environments without one, set `TEST_DATABASE_URL=""` — `cmd/riverpro/main_test.go::TestMigrateUpMainThenPro` already does this; the rest of the test suite will fail loudly without a DB.

### Parallelism gotcha

Go runs different test packages in parallel by default, and `riverprodatabasesql` and `riverpropgxv5` both run the **same** `riverprodrivertest.Exercise` suite against the **same** database. Anything that uses PostgreSQL-global state (e.g. `pg_try_advisory_xact_lock`) must use a **unique key per test invocation** — a hardcoded key races with the sibling driver package and produces flaky `Should be true` failures on `require.True(t, locked)`. See `riverpro_drivertest.go` `DocumentedExecutorAPI` for the fix pattern (`rand.Int63()`).

## Adding a new Pro executor method

1. Add the method to `ProExecutor` in `driver/driver.go`.
2. Implement it on `Executor` in the same file.
3. Add the call to `exerciseDocumentedExecutorAPI` in `driver/riverprodrivertest/riverpro_drivertest.go` (or whichever `exercise*` function fits the domain).
4. Both `riverprodatabasesql_test.go` and `riverpropgxv5_test.go` automatically pick it up — no per-driver changes needed.

## Generated code

`driver/internal/dbsqlc/*.go` and the matching `riverpro.sql.go` are generated by `sqlc v1.31.0` from `riverpro.sql` + `schema.sql` (config: `sqlc.yaml`). Header is `// Code generated by sqlc. DO NOT EDIT.`. Regenerate by editing the `.sql` inputs, not the Go output.

## Migrations

- Line name is `pro` (`MigrationLinePro` in `driver/driver.go`). Do not reintroduce the old `sequence` / `workflow` lines — the test suite asserts they are removed.
- Apply via the CLI: `go run ./cmd/riverpro migrate-up --database-url "$TEST_DATABASE_URL" --line pro [--schema <name>]`.
- For dry-run / SQL inspection: `migrate-get --line pro --version 1 --up`.
- The CLI also accepts `--dry-run`, `--max-steps`, `--target-version`. Defaults to `DATABASE_URL` env var if `--database-url` is empty.
- `002_add_periodic_admin_and_spec` extends `river_periodic_job` with `paused_at`, `kind`, `args` (jsonb), `queue`, `priority`, `max_attempts`, `tags`, `cron_expression`, `cron_timezone`, plus indexes `river_periodic_job_active_next_run_at_idx` and `river_periodic_job_kind_idx`. The Pro enqueuer loop relies on all of these.

## Durable Periodic Jobs

- Pro-only; opt in via `Config.DurablePeriodicJobs.Enabled = true`. OSS users continue to use upstream `river.Client.AddPeriodicJob` (the Pro enqueuer loop short-circuits when disabled).
- Pro owns `river_periodic_job` entirely: when enabled, the pilot's `PeriodicJobGetAll` / `KeepAliveAndReap` / `UpsertMany` overrides return `nil` so the upstream enqueuer does no work.
- Public admin API on `*Client[TTx]` (4 methods, each with a `Tx` variant = 8 total). All gated with `prodriver.ErrNotSupported` when disabled.
  - **`PeriodicJobUpsert`** — single method for all writes. Handles initial insert, schedule change, pause (`Paused: true` → `paused_at = now()`), and resume (`Paused: false` → `paused_at = NULL`). To change a row's schedule or pause state, call Upsert again with the same ID and the new spec.
  - `PeriodicJobDelete` — remove a row by ID.
  - `PeriodicJobGet` — fetch a single row by ID.
  - `PeriodicJobList` — paginate all rows.
- One-shot rows (`CronExpression == ""`): `river_job` row inserted and `river_periodic_job` row deleted in the same statement chain.
- Cron rows (`CronExpression != ""`): `river_job` row inserted; `river_periodic_job` row kept; `next_run_at` bumped to the next tick computed by the enqueuer loop using `github.com/robfig/cron/v3`. Driver stays free of the cron dep — it accepts the `NextRunAt` map from the client.
- **LISTEN/NOTIFY wakeup**: `PeriodicJobUpsert` and `PeriodicJobDelete` fire `pg_notify('<schema>.river_periodic_job_change', '')` in the same SQL statement chain, so the notification is rolled back if the change rolls back. Topic suffix is exported as `prodriver.PeriodicJobChangeTopicSuffix`; full topic is `<schema>.river_periodic_job_change` (or just the suffix when `Schema == ""`). Postgres topic length limit is 63 chars — keep schema names short.
- The enqueuer loop (`Start` → `periodicEnqueuerLoop`) opens a dedicated connection via `c.proDriver.GetListener(...)`, `LISTEN`s on the schema-prefixed topic, and runs `periodicEnqueueOnce` on every notification. A 30s safety-net ticker fires even in LISTEN mode to catch any missed notifications. Per-tick work is gated on a Postgres `pg_try_advisory_lock(bigint)` keyed on a per-process random int63 (`periodicEnqueuerLockKey`). Released at the end of each iteration.
- **Polling fallback**: if `Config.DurablePeriodicJobs.PollOnly` is true, or the driver does not support listeners (`!c.proDriver.SupportsListener()`), or the listener fails to `Connect`/`Listen` on startup, the loop falls back to `periodicEnqueuerPollingLoop` which polls at `DurablePeriodicJobs.PollInterval` (default 1s).
- Cron is parsed with `cron.NewParser(Minute|Hour|Dom|Month|Dow|Descriptor)` in `cronNextAfter`; standard 5-field spec plus `@hourly` / `@daily` / `@weekly` / `@monthly` / `@yearly` / `@every <duration>` descriptors.

## Common commands

```bash
# Run the full suite (needs DB):
go test ./...

# One package:
go test ./driver/riverpropgxv5/...
go test ./driver/riverprodatabasesql/...

# One subtest (note the slash):
go test -run 'TestDriverRiverProPgxV5/DocumentedExecutorAPI' ./driver/riverpropgxv5/

# Reproduce a flake:
go test -count=10 -run 'TestX' ./pkg/...

# Pure-Go unit tests only (no DB):
go test ./riverpro/ ./riverworkflow/ ./riverbatch/ ./riverencrypt/... ./driver/

# Vet the changed package:
go vet ./<pkg>/...

# Build the CLI:
go build ./cmd/riverpro
```

## Conventions

- `t.Parallel()` is the norm inside integration tests. Avoid hardcoded global identifiers (lock keys, fixed row IDs, fixed job kind names) — derive from the test schema or randomize.
- Use `riverdbtest.TestSchema` (not `TestSchemaPgx`) when the driver is wrapped through `riverpropgxv5.New` so the Pro migration line runs too.
- `riverprosharedtest.TestTxPgxPro` is the Pro-aware transaction helper when a test needs a `pgx.Tx` with both main and Pro migrations applied.
- Configuration should call `config.WithDefaults()` to fill unset timers / batch sizes before passing to `NewClient`.
- No linter config (`golangci-lint`), no Makefile, no CI, no README. `go vet` is the only static check configured. Don't add new toolchain assumptions without writing them down here.

## Things to avoid

- Editing files under `driver/internal/dbsqlc/` directly — they are sqlc output.
- Adding a `sequence` or `workflow` migration line. They are explicitly tested as removed (`driver/driver_test.go`).
- Hardcoded PostgreSQL advisory-lock keys in tests. Use `rand.Int63()` or derive from the schema.
- Importing `riverqueue.com/riverpro/...` — the module path is `github.com/divyam234/riverpro`.
